# Phase 0 — Static config sweeps

**Goal.** Characterize each pool's marginal-utility curve $V_\sigma(m_\sigma)$ empirically, by running config sweeps on the static knobs SGLang already exposes (`--mamba-full-memory-ratio`, `--max-loras-per-batch`, `--max-running-requests`, `--mem-fraction-static`). The output is (a) a per-pool $V_\sigma$ shape that Phase 2's online budgeter will fit at runtime, and (b) a "static-optimal" baseline that the online budgeter must beat.

No SGLang code changes in this phase. Setup, then sweeps, then plots.

## 1. Environment setup

### 1.1 System build dependencies (sudo, one-time)

Three system packages are needed:

- `libnuma-dev` and `libhwloc-dev` — `sgl-kernel`'s CMake pulls in `mscclpp` (Microsoft's allreduce library, hard-wired in `sgl-kernel/CMakeLists.txt`), which needs NUMA and HWLoc dev headers. Runtime libs are usually present; the dev headers are not.
- `protobuf-compiler` (`protoc`) — `python/pyproject.toml` builds a Rust extension (`sglang-grpc`) via `setuptools-rust` + `prost-build`. `prost-build` shells out to `protoc` to compile `.proto` files; without it, `cargo` fails with `Could not find PROTOC ...`.

Install all three at once:

```bash
sudo apt-get install -y libnuma-dev libhwloc-dev protobuf-compiler
```

Verify:

```bash

which protoc && protoc --version                   # libprotoc 3.x or 4.x
dpkg -l | grep -E 'libnuma-dev|libhwloc-dev|protobuf-compiler'
```

These are the only system-level packages this setup touches. Everything else lives inside `.venv`.

### 1.4 Source-build sgl-kernel (canonical path: `make build`)

Activate the sglang venv **first**, because `sgl-kernel/Makefile`'s `pip3 install dist/*.whl` resolves `pip3` from `PATH`. If another venv (`prelude/.venv`, conda, system) is on `PATH`, the wheel will land in the wrong site-packages and `import sgl_kernel` will fail later.

```bash
source .venv/bin/activate
make -C sgl-kernel build MAX_JOBS=$(nproc)
deactivate
```

What `make build` does (`sgl-kernel/Makefile:38-45`):
1. Installs build-time deps into the active venv: `scikit-build-core`, `isort`, `black`.
2. Initializes git submodules.
3. Runs `uv build --wheel ... --no-build-isolation -Cbuild-dir=build`. `--no-build-isolation` is the critical flag — it reuses our venv's torch 2.9.1+cu130 instead of fetching PyPI torch into a temp env.
4. `pip3 install dist/*.whl --force-reinstall --no-deps` into the active venv.

The Makefile sets `CMAKE_POLICY_VERSION_MINIMUM=3.5` by default (`Makefile:12`). This is required because `dlpack`, one of the FetchContent deps, declares `cmake_minimum_required` with a value <3.5 that CMake 4.x rejects.

Build duration on this box (8× H200, 256 cores, 4.2 TB free disk):
- **First-time clean build**: 30–45 minutes. Most of it is `FetchContent_Populate` cloning cutlass / DeepGEMM / fmt / triton / flashinfer / sgl-attn / mscclpp (≈1–2 GB total) and then nvcc compiling kernels with `--threads=32` per file across many `-gencode arch=...` targets.
- **Incremental rebuild** (e.g. after editing one .cu file): seconds to a few minutes, the CMake cache + ninja's incremental compile handle the rest.

Configure-time warnings that are safe to ignore: "Could NOT find IBVerbs" (RDMA, unused on this box), "library kineto not found" (PyTorch profiler, optional), "Failed to initialize NumPy" emitted inside the cmake build env.

### 1.7 Setup pitfalls

Five traps that cost an afternoon, recorded so the next person avoids them:

1. **Don't `uv pip install -e sgl-kernel`.** scikit-build-core in editable mode produces a binary-only wheel (no Python wrappers); the wrappers are expected to load from the source tree, where the .so files don't end up. `make build` produces a non-editable wheel that contains everything.
2. **Don't skip `--no-build-isolation`.** Default `uv pip install` builds in a temp env with its own torch (PyPI default, e.g. cu128). The resulting `sgl_kernel.so` links against PyPI torch's `c10_cuda_check_implementation(int, ...)`, but our venv's cu130 torch exports `c10_cuda_check_implementation(unsigned int, ...)`. Symbol mismatch at import time. `make build` uses `--no-build-isolation` and reuses our venv's torch.
3. **Activate the sglang venv before `make build`.** The Makefile's `pip3 install dist/*.whl` resolves `pip3` from `PATH`. If `prelude/.venv` (or any other venv) is on `PATH`, the wheel goes there instead of `sglang/.venv`. Always `source .venv/bin/activate` first.
4. **Don't worry about CMake 4.x policy errors.** The Makefile already sets `CMAKE_POLICY_VERSION_MINIMUM=3.5`. If you're invoking cmake directly, you need this — `dlpack` (FetchContent dep) requires it.
5. **First-time build clones ≈1-2 GB.** That's normal — `FetchContent_Populate` pulls cutlass/DeepGEMM/fmt/triton/flashinfer/sgl-attn/mscclpp into `sgl-kernel/build/_deps/`. Don't kill the build because it "looks idle" — it's cloning with no console output.
6. **`protoc` is needed before Step 1.3.** Without it, `uv pip install -e python` fails late (after most deps install) with a Rust `prost-build` error about `Could not find PROTOC`. It's only the Rust grpc extension that needs it; the rest of SGLang doesn't.
7. **System cmake on Ubuntu 24.04 is too old.** `/usr/bin/cmake` 3.28.3 doesn't know `cmake_policy(SET CMP0169|CMP0177 NEW)` that `sgl-kernel/CMakeLists.txt` sets. Install `cmake>=3.31` into the venv (§1.2 does this) and put `.venv/bin` first on `PATH` for `make build` (§1.4 does this). Symptom if missing: `CMake Error at CMakeLists.txt:9 (cmake_policy): Policy "CMP0169" is not known to this version of CMake`.
8. **uv venvs without `--seed` have no `pip`.** `sgl-kernel/Makefile`'s `install-deps` recipe calls bare `pip`. Without seeded pip, this falls through to `/usr/bin/pip` which PEP 668 blocks on recent Debian/Ubuntu. Always create the venv with `--seed` (§1.2).
9. **Run the SGLang server with `.venv/bin` on PATH.** SGLang's `jit_kernel/` JIT-compiles fused ops (rope, etc.) at first request via `tvm_ffi`, which shells out to `ninja` from `PATH` rather than from the calling Python. `python -m sglang.launch_server` (without PATH prefix) crashes with `FileNotFoundError: 'ninja'` even though the venv contains it. Launch with `PATH="$PWD/.venv/bin:$PATH" python -m sglang.launch_server ...`.

## 2. Models and traces

Three sweeps, one per non-paged-KV pool, on a single H200. Each holds two pools fixed and varies the budget knob for the third pool (or for the global mem fraction); throughput, latency, and per-pool stats from `/get_server_info` and Prometheus give the empirical $V_\sigma(m_\sigma)$ shape.

| Sweep | Model | Knob varied | Other pools/state |
|---|---|---|---|
| **1. KV ↔ DeltaNet (SSM)** | `Qwen/Qwen3.5-35B-A3B` | `--mamba-full-memory-ratio` ∈ {0.1, 0.3, 0.5, 0.7, 0.9} | LoRA off; prefix cache on (default) |
| **2. KV ↔ LoRA** | `Qwen/Qwen3-4B` + N synthetic LoRA adapters | `--max-loras-per-batch` ∈ {1, 2, 4, 8, 16, 32} | Prefix cache on (default); no SSM |
| **3. KV ↔ prefix-cache** | `Qwen/Qwen3-8B` | `--max-running-requests` ∈ {16, 32, 48, 64, 96, 128} | LoRA off; no SSM |

**Why these specific models on this box (single H200 = 143 GiB):**

- **Sweep 1: Qwen3.5-35B-A3B.** 35 B params total, 3 B activated per token (MoE) — a real DeltaNet hybrid with both full-attention and DeltaNet layers. BF16 weights ≈ 70 GB, leaving ~70 GB for KV + SSM state to share. Already cached at `~/.cache/huggingface/hub/models--Qwen--Qwen3.5-35B-A3B/`.
- **Sweep 2: Qwen3-4B + LoRA.** Small base model (≈8 GB BF16) so the LoRA cache pool size is the binding constraint, not weight memory. Adapters synthesized with random initialization at rank 16 / 64 / 128 to vary per-adapter footprint.
- **Sweep 3: Qwen3-8B.** Pure full-attention; multi-turn workload from `benchmark/hicache/bench_multiturn.py` saturates the prefix cache. Varying `--max-running-requests` shifts the split between protected (active-request) blocks and evictable (prefix-cache) blocks under the same total HBM budget.

**Workload driver:** `python -m sglang.bench_serving --backend sglang ...` for Sweeps 1/2 (steady-state throughput) plus `benchmark/hicache/bench_multiturn.py` for Sweep 3 (prefix-cache pressure). Both are stock SGLang tools, no custom drivers needed at this phase.

## 3. Sweep design

For each (sweep, knob value) point we:

1. **Launch SGLang server** with the knob and pool flags set, on GPU 2 (idle by `.env`'s `CUDA_VISIBLE_DEVICES=2` — switch per run if needed). `--enable-metrics` exposes Prometheus counters at `/metrics`.
2. **Wait for server health** (poll `/health` until 200, max 5 min boot).
3. **Capture baseline state** from `/get_server_info`: `max_total_tokens`, `max_loras_per_batch`, `mamba_full_memory_ratio`, `swa_full_tokens_ratio`, etc. Pin these as the "static partition" we're sampling.
4. **Run the workload** for a fixed duration / request count. For Sweep 1/2: `python -m sglang.bench_serving --backend sglang --dataset-name random --num-prompts 1000 --random-input 512 --random-output 64 --request-rate 32`. For Sweep 3: `python benchmark/hicache/bench_multiturn.py --num-clients 256 --max-parallel 128 --num-rounds 5 --request-rate 8`. Save bench output JSON.
5. **Scrape `/metrics` once at end** and write to `dev/0/sweep<N>/<knob>.metrics.txt`. The relevant series:
   - `sglang:token_usage` — fraction of paged KV in use (0–1)
   - `sglang:cache_hit_rate` — prefix-cache hit rate
   - `sglang:gen_throughput` — generation throughput (tok/s)
   - `sglang:num_running_reqs`, `sglang:num_queue_reqs`
   - For hybrid: `sglang:full_token_usage`, `sglang:swa_token_usage`, `sglang:mamba_usage` (only present when the model uses those pools)
6. **Kill server**, wait for GPU to clear, move to next knob value.

The sweep driver lives at [`0/sweep_driver.sh`](0/sweep_driver.sh). Output layout:

```
dev/0/
├── setup.log
├── sweep_driver.sh
├── sweep1_kv_vs_ssm/
│   ├── ratio_0.10.bench.json
│   ├── ratio_0.10.metrics.txt
│   ├── ratio_0.10.server_info.json
│   ├── ... (one set per knob value)
│   └── results.csv         # consolidated table
├── sweep2_kv_vs_lora/...
└── sweep3_kv_vs_prefix/...
```

Each sweep yields a `results.csv` with columns: `knob_value, throughput_tps, ttft_p50, ttft_p99, kv_usage, prefix_hit, ssm_usage, lora_hit_rate, ...`. The CSV is the empirical $V_\sigma(m_\sigma)$ — Phase 2's online budgeter fits a curve through it.

Sweep order (priority): **1 (KV ↔ SSM)** first because it's the most paper-relevant — it's the only sweep where two **physical** state pools share the same byte budget today via `mamba_full_memory_ratio`. Sweeps 2 and 3 are next; they're cleaner (LoRA and prefix have separate budgets already) but less novel.

## 4. Results

### 4.1 Sweep 1 — KV ↔ DeltaNet (mamba_full_memory_ratio)

**Setup.** Single H200, `Qwen/Qwen3.5-35B-A3B`, `--mem-fraction-static 0.85`. Workload: `bench_serving --dataset-name random --num-prompts 1000 --random-input 1024 --random-output 256 --request-rate 32`. Knob: `--mamba-full-memory-ratio` ∈ {0.1, 0.3, 0.5, 0.7, 0.9}. Each point: cold-load → bench → metrics scrape every 2 s during the run. Driver: [`0/sweep_driver.sh`](0/sweep_driver.sh). Raw data: [`0/sweep1_kv_vs_ssm/`](0/sweep1_kv_vs_ssm/).

The flag is `mamba_state_memory / full_kv_memory`; with the rest-memory budget fixed, higher ratio means more memory to mamba state, less to KV (`model_runner_kv_cache_mixin.py:111-118`).

**Results.**

| ratio | mamba share of pool budget | input TPS | output TPS | mean TTFT (s) | P99 TTFT (s) | mamba_usage peak | full_token_usage peak | max_running |
|------:|---------------------------:|----------:|-----------:|--------------:|-------------:|-----------------:|----------------------:|------------:|
| 0.1   | 9 %                        |     3 039 |        764 |          69.9 |        132.2 |             0.66 |                 0.008 |          26 |
| 0.3   | 23 %                       |     3 793 |        953 |          49.7 |         97.6 |             0.66 |                 0.023 |          67 |
| 0.5   | 33 %                       |     5 973 |      1 501 |          23.5 |         48.5 |             0.66 |                 0.037 |          97 |
| 0.7   | 41 %                       |     6 890 |      1 732 |          17.2 |         36.9 |             0.66 |                 0.050 |         119 |
| 0.9   | 47 %                       |     7 648 |      1 922 |          13.6 |         29.4 |             0.66 |                 0.064 |         138 |

![Sweep 1](0/sweep1_kv_vs_ssm/plot.png)

**Read.**

- **DeltaNet state is the binding pool, not KV.** Across all ratios, the DeltaNet state pool saturates at ~66 % utilization (its admission-time concurrency limit per `model_runner_kv_cache_mixin.py`) while the paged KV pool peaks at <7 %. The KV pool has gobs of headroom this entire sweep; it is *never* the bottleneck.
- **`max_running_reqs` scales linearly with the mamba budget**: 26 → 67 → 97 → 119 → 138. This is the per-request DeltaNet slot count — every concurrent request needs one mamba slot regardless of attention/decode phase.
- **Throughput grows 2.5×** (3.0 K → 7.6 K input TPS) and **TTFT shrinks 5×** (70 s → 13.6 s mean) as we shift memory away from KV (which doesn't need it) toward DeltaNet (which is the bottleneck). The curve flattens past ratio=0.7 — the second half of the sweep buys ~10 % throughput per ~6 percentage-point shift, vs ~50 % per ~14 pp shift in the first half. Concave $V_{\text{SSM}}(m_{\text{SSM}})$, classic decreasing-marginal-utility shape.
- **For this workload, the default `--mamba-full-memory-ratio=0.9` is approximately right** — but the sweep stops at 0.9 because the SGLang code path uses `m / (1+m)` and ratio>1 gets clamped. Pushing further (e.g. by increasing `mem-fraction-static`) would likely show diminishing-returns saturation and tell us the elbow precisely.

**What this means for the paper.**

This is exactly the pattern the budgeter design predicts — the marginal utility of the two pools at the static default is asymmetric, and which pool is binding is workload-dependent (here: prefill-heavy 1024-in/256-out → mamba binds; for KV-heavy long-output workloads we'd expect the curves to flip). $V_{\text{KV}}(m_{\text{KV}})$ has near-zero slope in this regime; $V_{\text{SSM}}(m_{\text{SSM}})$ has steep concave slope. A workload-aware budgeter that reads pool pressure each phase and shifts memory toward the binding pool can move the operating point along these curves without retuning the deployment-time knob.

The TTFT improvement (5× under the same mem-fraction) is also a useful talking point — it's not just a throughput knob, it directly affects user-visible latency.

**Caveat.** Bench duration was 85–187 s per point. The 5× spread in duration across knob values is itself a signal — at low ratio, bench takes much longer because the queue stalls. Within a single workload pattern, the static-optimal is well-defined; under shifting workload it isn't, which is the whole motivation for Phase 2.

### 4.2 Sweep 2 — KV ↔ LoRA

**Setup.** `Qwen/Qwen3-4B` base + 32 synthetic rank-16 LoRA adapters (random init via PEFT, generation script: [`0/make_synthetic_loras.py`](0/make_synthetic_loras.py)). `--mem-fraction-static 0.7 --enable-lora --max-loaded-loras 32 --lora-paths lora_0=... lora_31=...`. Knob: `--max-loras-per-batch` ∈ {1, 2, 4, 8, 16, 32}. Workload: `bench_serving --dataset-name random --num-prompts 1000 --random-input-len 512 --random-output-len 64 --request-rate 32 --lora-name lora_0..lora_31 --lora-request-distribution uniform`. Driver: [`0/sweep_driver_parallel.sh`](0/sweep_driver_parallel.sh) (run on 6 idle GPUs in parallel — wall clock 64 s vs ~6 min sequential). Raw data: [`0/sweep2_kv_vs_lora/`](0/sweep2_kv_vs_lora/).

**Results.**

| max_loras_per_batch | input TPS | output TPS | mean TTFT (ms) | P99 TTFT (ms) | KV usage peak | duration (s) |
|--------------------:|----------:|-----------:|---------------:|--------------:|--------------:|-------------:|
|                   1 |     5 652 |        707 |          7 047 |        14 858 |          0.6% |           64 |
|                   2 |     6 442 |        806 |          3 586 |         7 476 |          0.7% |           64 |
|                   4 |     7 072 |        885 |          1 861 |         4 104 |          0.7% |           64 |
|                   8 |     7 258 |        908 |          1 006 |         2 493 |          1.0% |           64 |
|                  16 |     7 462 |        934 |            309 |         1 123 |          1.6% |           64 |
|                  32 |     7 556 |        945 |             74 |           526 |          1.3% |           64 |

![Sweep 2](0/sweep2_kv_vs_lora/plot.png)

**Read.**

- **TTFT is the dominant signal here, not throughput.** Throughput grows from 5.6 K → 7.6 K input TPS (+34 %) across the full 32× sweep. TTFT collapses by **95×** (7.0 s → 74 ms). The reason: with `max_loras_per_batch=1`, every batch can serve only one adapter at a time, so requests targeting any other adapter wait an entire batch round before getting prefill — that's the 7-second mean and 15-second tail. Past 8, every active adapter usually fits in one batch and the stalls vanish.
- **KV pool is irrelevant here.** Peak KV utilization stays at 0.6–1.6 % across all knob values. The base model is small (≈8 GB BF16) and the workload is light; the bottleneck is purely adapter-cache scheduling, not memory.
- **Concave $V_{\text{LoRA}}(m_{\text{LoRA}})$ with a sharp elbow at 8.** From 1→8 the marginal TTFT improvement is ≈900 ms per doubling of `max_loras`; from 8→32 it's ≈250 ms per doubling. The throughput curve has the same shape but flatter — it saturates at 16. So a workload with up to 32 hot adapters has $V_{\text{LoRA}}$ shaped like a hockey stick.
- **The static default `--max-loras-per-batch=8` is nearly optimal *for this workload* but not for one with more concurrency-spread.** A traffic mix with N > 8 hot adapters and tight TTFT SLOs would want `max_loras=16` or `32`; one with only 1–2 adapters in flight would be fine at `max_loras=1`. That's the workload-dependence the budgeter exploits.
- **Caveat.** With 32 random-init adapters and uniform selection across them, every request hits a different adapter ~97% of the time. A real workload's LoRA traffic is typically skewed (one or two hot adapters dominate); we'd expect the elbow to shift left under skew. Phase 2 should re-run with `--lora-request-distribution skewed` to characterize that shape.

### 4.3 Sweep 3 — KV ↔ prefix cache

**Setup.** `Qwen/Qwen3-8B`, `--max-running-requests 64`. Knob: `--mem-fraction-static` ∈ {0.3, 0.4, 0.5, 0.65, 0.8}. Workload: `bench_multiturn.py --num-clients 64 --max-parallel 32 --num-rounds 6 --request-length 512 --output-length 128 --request-rate 8 --distribution poisson`. Each client runs 6 rounds; round N's prompt includes round N−1's response — produces real round-to-round locality on a per-client prefix. Driver: [`0/sweep_driver_multiturn.sh`](0/sweep_driver_multiturn.sh) (sequential; was already running on GPU 2 when the parallel driver was added later for Sweep 2). Raw data: [`0/sweep3_kv_vs_prefix/`](0/sweep3_kv_vs_prefix/).

**Two earlier attempts were abandoned and kept for reference:**
- `sweep3_kv_vs_prefix.attempt1_too_light/`: KV pool over-provisioned (peak 2 % util); knob `max-running-requests` never bound, throughput plateaued.
- `sweep3_kv_vs_prefix.attempt2_no_locality/`: pressured KV (peak 42 %) but burst-arrival random workload meant first occurrence of each prefix was prefilled in parallel with subsequent ones — `cache_hit_rate` stayed 0 throughout.

**Results.**

| mem_fraction | input TPS | output TPS | mean TTFT (ms) | P99 TTFT (ms) | KV peak | prefix hit rate | duration (s) |
|-------------:|----------:|-----------:|---------------:|--------------:|--------:|----------------:|-------------:|
|         0.30 |     2 103 |        127 |           27.4 |          39.8 |    46 % |          75.3 % |          386 |
|         0.40 |     2 106 |        128 |           27.0 |          37.6 |    28 % |          75.8 % |          385 |
|         0.50 |     2 106 |        128 |           26.7 |          37.1 |    24 % |          75.8 % |          385 |
|         0.65 |     2 041 |        124 |           27.0 |          35.4 |    15 % |          75.8 % |          397 |
|         0.80 |     2 088 |        127 |           27.0 |          36.9 |    13 % |          75.8 % |          388 |

![Sweep 3](0/sweep3_kv_vs_prefix/plot.png)

**Read.**

- **Prefix cache hit rate is workload-pinned at ~75.8 %, NOT pool-size-determined in this regime.** Hit rate is essentially flat at every mem-fraction tested (0.30 dips by 0.005 — half a percentage point — vs the others). The 75.8 % is structural: of the 6 rounds × 64 clients = 384 requests, the first round of each client is a cold miss; rounds 2–6 hit on the per-client prefix. With 1 cold + 5 warm per client, the asymptotic hit rate is 5/6 = 83.3 % minus the partial-prefix overhead — call it ~76 %, exactly what we see.
- **KV pool stays uncongested even at the tightest knob.** Peak `full_token_usage` rises 13 % → 46 % as we tighten mem-fraction 0.80 → 0.30. The 64-client × 6-round workload at 8 rps just doesn't stress the 80 GB+ KV pool of Qwen3-8B. A stress test would need either many more clients or a much larger system prompt — left to Phase 1.
- **Throughput, TTFT essentially constant.** Within ±2 % across the sweep. The bottleneck is the bench's request rate (8 rps × multi-turn dependency = effective ~5–6 rps after first round), not the GPU. Without bench-side pressure we can't observe the pool-size-vs-throughput tradeoff cleanly.
- **Why this is still informative.** The take-away from Sweep 3 is the *opposite* of Sweep 1: the prefix cache pool **doesn't bind** for this workload regardless of how much memory we give it. Hit rate is determined by workload structure (round count, locality pattern), not by pool size — the marginal utility $V_{\text{prefix}}(m_{\text{prefix}})$ saturates well below the smallest tested mem-fraction. So a static knob that *over-budgets* the prefix cache wastes memory that could be elsewhere; a dynamic budgeter could detect "$V_{\text{prefix}}$ is flat → shrink prefix cache, give to whichever pool isn't saturated".

**Caveat.** The single-pool view here is misleading on its own. For a workload mix that combined this multi-turn traffic with Sweep 1's hybrid traffic on the same engine, the budgeter would see flat $V_{\text{prefix}}$ and steep $V_{\text{SSM}}$ and reallocate — exactly the gap a static `mem-fraction-static` setting can't bridge.

## 5. Discussion

### 5.1 What Phase 0 found

Across three independent sweeps, each isolating one non-paged-KV pool against the others held fixed:

- **Sweep 1 (KV ↔ DeltaNet on Qwen3.5-35B-A3B).** $V_{\text{SSM}}(m_{\text{SSM}})$ is steeply concave; the binding pool for prefill-heavy traffic is DeltaNet state, *not* KV. KV utilization stays under 7 % across the full sweep. Throughput grows 2.5×, TTFT shrinks 5×, as memory shifts from KV to DeltaNet.
- **Sweep 2 (KV ↔ LoRA on Qwen3-4B + 32 adapters).** $V_{\text{LoRA}}(m_{\text{LoRA}})$ is hockey-stick: dramatic TTFT improvement (95×) from `max_loras` 1→8, then diminishing returns 8→32. KV pool unutilized — bottleneck is purely adapter-swap scheduling.
- **Sweep 3 (KV ↔ prefix-cache on Qwen3-8B, multi-turn).** $V_{\text{prefix}}(m_{\text{prefix}})$ is *flat* for this workload — the multi-turn structure pins the hit rate at ~75.8 % regardless of mem-fraction (0.30 → 0.80). The prefix cache earns its budget only up to the working-set size; beyond that, additional bytes go to waste.

Two negative results from intermediate Sweep 3 attempts are themselves informative:
- A pure-random workload pressuring the KV pool produces `cache_hit_rate=0` because prompts have no shared prefixes — the prefix cache is dead weight.
- A burst-arrival shared-prefix workload also produces `cache_hit_rate≈0` because all 4096 requests reach the queue before the first prefix is committed to the cache. Prefix cache only earns its keep when temporal locality permits — and the budget the cache *deserves* depends sharply on whether the workload generates that locality.

### 5.2 Implications for the paper

Three consistent observations across the sweeps justify the budgeter design:

1. **The binding pool is workload-dependent.** Sweep 1 shows DeltaNet is bottleneck for prefill-heavy hybrid traffic; Sweep 2 shows LoRA-cache is bottleneck for multi-tenant adapter traffic; Sweep 3 (preliminary) shows prefix-cache only earns budget under round-to-round locality. None of these workloads is bottlenecked by the same pool. A static deployment-time partition is by definition wrong for at least two of the three.
2. **Marginal-utility curves $V_\sigma(m_\sigma)$ are real and easy to fit.** Each sweep produced a clean concave curve with a definable elbow. Phase 2's online budgeter only needs to keep these curves up to date (a few bytes of state per pool, updated each scheduler tick) and equalize $\partial V_\sigma / \partial m_\sigma$ via Lagrange multiplier. The curves don't need to be exact — they just need to identify which pool gets the next byte.
3. **The "static-optimal" baseline is recoverable from these sweeps.** For each of the three workload patterns, we now have the empirical optimum point (or the point on the saturating end of the curve, where applicable). When Phase 2 runs the online budgeter against the same workload, it should match that point — and across workload mix, it should beat the *single static* default by Sweep-1-magnitude factors.

### 5.3 What's missing / next-phase work

- **Skewed LoRA traffic.** Sweep 2 used uniform-random LoRA selection. Production traffic is typically skewed (Zipf-like). The elbow of $V_{\text{LoRA}}$ likely shifts left under skew. To redo with `--lora-request-distribution skewed` in Phase 1.
- **Joint sweeps.** Phase 0 isolated one pool at a time. Phase 2's budgeter has to handle multiple binding pools simultaneously (e.g. SSM and LoRA both pressed). The cross-pool curves haven't been characterized — that's a Phase 1 / 2 task.
- **More $V_{\text{KV}}$ data points.** Across all three sweeps the KV pool stayed under-utilized. A separate KV-stress sweep (long context, no LoRA, pure-attention model) would be useful to characterize $V_{\text{KV}}(m_{\text{KV}})$ in the regime where it does bind.
- **Phase shifts.** The whole motivation for the budgeter is workloads whose binding pool changes over time. We haven't measured such a phase shift directly. Phase 1's instrumentation should make that observable, and Phase 2's policy reaction is the demo.
