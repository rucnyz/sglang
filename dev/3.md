# Phase 3 — Layer 1: state-recoverable prefix cache for hybrid LLMs

**Status:** planning. After 2026-04-29 restructuring, Phase 3 is the SGLang-side implementation of the paper's Layer 1.

**Relationship to Phase 2.** Phase 2's cross-pool VMM (= Layer 2) needs Layer 1 to demo a real win — otherwise the prefix cache holds dead weight on hybrid models and reallocating it doesn't move the needle. The original Phase 3d (physical pool resize via VMM) has been **promoted to Phase 2.2e** — it's no longer optional; it's the cross-pool actuator that makes the paper claim true.

## 3a. Input-token-only indexing

**Problem.** SGLang's `RadixCache` (and `UnifiedRadixCache`) inserts every committed sequence into the radix tree, including CoT / reasoning / final output tokens. In agent / multi-turn / reasoning workloads, those output tokens are mostly one-shot — they almost never appear as a prefix in a future request. They occupy cache budget without earning hit-rate.

**Approach.**
- New env-flag `SGLANG_PREFIX_CACHE_INPUT_ONLY=1` (default off so production behavior is unchanged).
- In `cache_finished_req` / `cache_unfinished_req` (the hooks where SGLang installs a request's tokens into the radix tree), truncate the inserted token list to the *prompt* portion (`req.origin_input_ids` length), dropping the generated tail.
- Patch surface: ~30 LoC in `python/sglang/srt/mem_cache/radix_cache.py` and `unified_radix_cache.py`.

**Expected impact on Phase 2 budgeter.** With output tokens out of the index, prefix-cache's effective working set shrinks → the same $m_{\text{prefix}}$ holds proportionally more *useful* prefixes → `cache_hit_rate` goes up at the same pool size → $V_{\text{prefix}}(m_{\text{prefix}})$ gets steeper. The budgeter then has a better reason to allocate to prefix-cache when traffic shows real prefix locality, and a clearer signal to deallocate when it doesn't.

**Validation.** Re-run Phase 0 Sweep 3's multi-turn workload with `SGLANG_PREFIX_CACHE_INPUT_ONLY=1`. Hit rate should stay the same or rise (multi-turn shares input prefix only); KV evictable should drop (less garbage in the cache); throughput marginally higher because the cache is less busy on lookup. Then re-run with the budgeter ON: budget allocation to prefix should differ.

## 3b. Two-granularity tree with SSM state recovery

**Problem.** SGLang's `MambaPool` allocates one DeltaNet/SSM state slot per concurrent request and updates it in-place. There is no checkpointing at chunked-prefill boundaries. So a hybrid model's prefix-cache hit on the full-attention KV side is *not directly usable*: the SSM state at that prefix boundary doesn't exist anywhere — the new request would have to re-prefill the SSM layers from token 0 even when the matching KV is hot. Token-level prefix matching alone is not enough for hybrid models; **state-level matching** is required.

This explains the Phase 0 Sweep 3 finding that the prefix pool is "flat-utility" even on multi-turn hybrid traffic — half the value of a hit (the SSM half) is unrecoverable, so the marginal value of a bigger prefix cache is muted.

**Approach (sketch — significant work, ~500 LoC).**
- Two-granularity radix tree (paper §3.1): small-page nodes carry a span of `hash_page_size` (default 512) tokens of paged-attention KV; big-page nodes additionally own a snapshot of the recurrent state at the page boundary on every linear-attention layer.
- At each chunked-prefill boundary that lines up with a big-page multiple (e.g. `K=16` × 512 = 8K tokens), snapshot the per-layer SSM state from the live `MambaPool` slot into the big-page node's snapshot tensor.
- Extend the radix tree's leaf data to record which big-page snapshot satisfies each long prefix.
- On cache hit at a node with a snapshot, copy the snapshot back into the new request's MambaPool slot before resuming decode. Decode resumes from token $L \cdot K$ on **all** layers, full-attention and recurrent alike — no re-prefill.
- Small-page nodes between snapshots remain "token-only hits"; falling back means re-prefilling at most $K$ small pages of suffix from the last big-page snapshot rather than from token 0.

**Expected impact.** $V_{\text{prefix}}$ on hybrid models gets *much* steeper — prefix hits now carry full state. Phase 0 Sweep 3's flat curve becomes a real curve. Combined with Sweep 1's "DeltaNet is the binding pool" finding, the budgeter has a real two-pool tug-of-war to arbitrate (active SSM slots vs prefix-cached SSM snapshots), which is the paper's most interesting demo case.

**Risk / blockers.**
- **Snapshot/restore cost** on the GPU ranges from non-trivial to large depending on how big the SSM state is per layer. For Qwen3-Next / Qwen3.5 the per-layer state is a few hundred KB; for Mamba-3-style designs it could be larger.
- **Chunked-prefill alignment**: snapshots only land on boundaries that are multiples of the big-page size. SGLang's `chunked_prefill_size` is a deployment knob today; making it cooperate with `linear_att_page_block_num` requires coordination — wrong alignment ⇒ no usable snapshots.
- **`(prefix, lora_name)` keying when LoRA is active.** LoRA adapters perturb the mamba-layer weights, so the SSM state at a prefix boundary depends on which adapter was active. A snapshot keyed by prefix tokens alone is unsafe to reuse across adapters; the cache must be keyed by `(prefix_hash, lora_name)`. The paper's Layer 1 evaluation runs without LoRA in the baseline configuration, so this is a "nice to have" extension; required if a future workload joins LoRA + hybrid + prefix locality.
- **Snapshot-aware eviction policy** (paper §3.2). A prefix block that has an SSM snapshot attached is more valuable to keep than a token-only block — restoring from a snapshot is materially cheaper than re-prefilling. The unified-radix LRU should weight nodes by hits-per-byte: a big page's weight is `n_hits / (KV_bytes + snapshot_bytes)`, a small page's weight uses only KV bytes. Without this weighting, the unweighted LRU evicts big pages first (they're heaviest), defeating the design.
- **Big-page size could itself be a budgeter knob.** A static `linear_att_page_block_num` is wrong across workload mix — short-prefix-dominated traffic ⇒ smaller big pages (less wasted snapshot memory); long-prefix traffic ⇒ larger big pages (better state-recovery batching). Adding this as another budgeter action surface is a natural extension once the snapshot machinery exists; not in the paper's headline scope.

This is the highest-impact-but-also-highest-effort sub-phase.

## 3c. Tier the prefix cache to host DRAM

**Problem.** Even with 3a + 3b, the prefix-cache pool is bounded by HBM. For agent workloads with very long context, prefix-cache size is the bottleneck.

**Approach.**
- Big pages are page-aligned chunks of (KV bytes + snapshot bytes). They are the natural unit to demote to host DRAM: a single `cudaMemcpyAsync` per big-page node moves both the KV blocks and the recurrent-state snapshot together.
- Small pages do not tier — their cost-of-promotion is dominated by setup overhead, not data volume, so demoting and re-promoting them is rarely a win.
- Standard 3-level cache hierarchy (GPU → host DRAM → disk LRU); promotion is on-demand at lookup time.

**Expected impact.** Decouples prefix-cache size from HBM. For long-context agent workloads, this can grow effective prefix capacity 5–10×. For the paper, this is "scales out without changing the substrate" framing.

## 3.5 Why we are not adopting an external implementation

We considered whether to integrate an existing within-pool snapshot implementation rather than build our own. Two candidates surfaced in the literature/code review:

- **Marconi (Pan et al., MLSys'25)**: closest peer; re-derives admission/eviction around in-place SSM state. Academic work, no public production-ready implementation that fits SGLang's pool model.
- **A snapshot-pool patch in another open-source serving engine**: ships a CoT-exclusion + page-aligned snapshot design, but its snapshot pool lives on **pinned host CPU** (verified via subagent code-level audit, 2026-04-29), not GPU. Adopting it does not give us a GPU-resident $V_{\text{prefix}}$ slope — the budgeter still sees flat marginal utility on the GPU side.

Both prior efforts validate the design direction (token-only indexing + page-aligned state snapshots). Neither directly delivers the GPU-resident snapshot tier the cross-pool budgeter needs to act on. Phase 3 implements our own variant on SGLang.
