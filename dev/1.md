# Phase 1 — Read-only joint pressure dashboard

**Status:** in progress (started 2026-04-29).

**Goal.** Surface per-pool pressure signals (eviction rate, LoRA hit rate, prefix evictable bytes) that Phase 2's online budgeter will read every ~1 s. **No allocator changes; instrumentation only.**

**Prerequisite.** Phase 0 done (see [`0.md`](0.md)).

---

## 1. Audit — what SGLang already exposes

Booted Qwen3-4B with `--enable-lora --max-loras-per-batch 4` + 8 LoRA adapters and probed `/metrics` after a few generation requests. SGLang exports **67 distinct `sglang:*` metric names**. Phase 1's signal contract is the *subset* below — these are what Phase 2's budgeter will subscribe to. Already-exposed; no patches needed.

### 1.1 Per-pool pressure (the four pools)

| Pool | Gauge(s) | Notes |
|---|---|---|
| **paged KV (full attention)** | `kv_used_tokens` / `kv_available_tokens` / `max_total_num_tokens`; `token_usage`; `full_token_usage` | `kv_used_tokens + kv_evictable_tokens + (free) = kv_available_tokens`. `token_usage` is the in-use fraction. |
| **paged KV (sliding-window)** | `swa_token_usage` | Only nonzero on SWA models (Qwen2.5-coder, Gemma 2, etc.). |
| **DeltaNet / Mamba SSM state** | `mamba_usage` | Fraction of allocated SSM slots in use. Only nonzero on hybrid models (Qwen3.5, Qwen3-Next, Nemotron-H, Jamba). |
| **LoRA adapter cache** | `lora_pool_slots_used` / `lora_pool_slots_total` / `lora_pool_utilization` | Only emitted when `--enable-lora`. Slots_total = `max_loaded_loras`. |
| **prefix cache (lives in KV)** | `kv_evictable_tokens`; `cache_hit_rate`; `cached_tokens_total` | Prefix cache occupies the evictable portion of the paged-KV pool. `cache_hit_rate` is the rolling lookup hit ratio. |

The "four pools" framing in the paper maps onto SGLang as follows:
- KV + prefix cache **share** one physical pool (the paged-KV `BlockPool`) but are observable separately via `kv_used_tokens` (active) vs `kv_evictable_tokens` (prefix-cached & not pinned).
- SSM, LoRA each have their own physical pool with dedicated metrics.

### 1.2 Eviction / preemption rate

| Signal | Source | Use |
|---|---|---|
| `num_retracted_reqs` (gauge) | requests currently retracted (mid-flight pulled out due to KV pressure) | budgeter trigger: `>0` for >5 s ⇒ KV under-budgeted |
| `num_retractions_{count,sum,bucket}` (histogram) | per-request retraction count distribution | rate(count) over 30 s ≈ retraction rate |
| `num_paused_reqs` (gauge) | currently paused (admission-time preemption) | budgeter trigger: same as retracted; paused has lower latency cost than retracted |

For LoRA-cache evictions and prefix-cache evictions the only built-in signals are indirect:
- LoRA: when `lora_pool_slots_used == lora_pool_slots_total` and a new adapter request arrives, an LRU eviction fires inside `LoRAManager`. Not exported as a counter; would need a small patch (deferred to Phase 2 if needed).
- Prefix cache: `kv_evictable_tokens` *decreasing* in the same step that `kv_used_tokens` increases is an eviction event. Computable client-side as a delta.

### 1.3 Throughput, queue, latency

| Signal | Use |
|---|---|
| `gen_throughput` | tokens/sec (windowed) |
| `num_running_reqs`, `num_queue_reqs`, `num_grammar_queue_reqs`, `num_*_prealloc_queue_reqs` | per-stage queue depth — important secondary signal: a binding pool typically grows queue depth while keeping pool ≈100 % utilized |
| `time_to_first_token_seconds_*`, `queue_time_seconds_*` | latency distribution histograms |
| `prompt_tokens_histogram_*`, `generation_tokens_histogram_*` | per-request size distribution |
| `max_running_requests_under_SLO` | SGLang's own admission-control estimate; useful as an SLO-pinned reference point |

### 1.4 Cumulative counters (for rate-derivation)

| Counter | Rate semantics |
|---|---|
| `prompt_tokens_total`, `generation_tokens_total`, `cached_tokens_total`, `realtime_tokens_total` | input/output/cache-hit token rates |
| `num_requests_total`, `num_retracted_requests_total` | request and retraction rates |
| `evicted_tokens_total`, `eviction_duration_seconds_*` | eviction rate (only fires when an eviction actually happens) |

### 1.5 Gaps Phase 1 deliberately leaves alone

Two signals the budgeter will eventually want but Phase 1 does **not** add:
- **LoRA request-level hit/miss** (was the requested adapter already hot?). Not exported; can be approximated by `lora_pool_utilization == 1.0` + arrival rate. Phase 2 may add a small patch (~30 LOC in `lora_manager.py`).
- **Per-pool capacity in bytes** (only token counts are exposed). Conversion `tokens × bytes_per_token` is constant per model; Phase 2 can compute it locally from `/get_server_info`.

## 2. Sampling client

`dev/1/sample_metrics.py` — polls `http://host:port/metrics` every 1 s and writes one JSONL line per scrape with the **24 signals** Phase 2 cares about:

```
{"ts": 1777461234.567,
 # paged KV
 "kv_max": 347879, "kv_used": 7, "kv_evictable": 314, "kv_available": 347558,
 "token_usage": 0.0, "full_token_usage": 0.0, "swa_token_usage": 0.0,
 # SSM
 "mamba_usage": 0.0,
 # LoRA
 "lora_used": 1, "lora_total": 4, "lora_util": 0.25,
 # prefix
 "cache_hit_rate": 0.83, "cached_tokens_total": 384,
 # eviction / preemption
 "num_retracted": 0, "num_paused": 0, "num_retracted_total": 0,
 "evicted_tokens_total": 0,
 # queue / throughput / latency
 "num_running": 0, "num_queue": 0, "gen_throughput": 0.0,
 "ttft_count": 12, "ttft_sum": 0.04,    # for rate = (count_t - count_t-1) / dt
 "prompt_tokens_total": 132, "generation_tokens_total": 96}
```

Run as a sidecar to any SGLang server. Output: one JSONL file per validation run.

## 3. Dashboard renderer

`dev/1/dashboard.py` — reads a JSONL, renders a 3×2 grid:

| Panel | Series |
|---|---|
| KV pool | `kv_used_tokens / kv_max`, `kv_evictable / kv_max` (stacked area) |
| SSM pool | `mamba_usage` |
| LoRA pool | `lora_used / lora_total` |
| Prefix-cache hit rate | `cache_hit_rate` (rolling 10 s mean) |
| Throughput / queue | `gen_throughput` and `num_queue` on twin Y axes |
| Eviction / retraction rate | `evicted_tokens_total` rate, `num_retracted_total` rate |

PNG output. Optional `--live` mode opens a window and updates every second.

## 4. Validation workload

`dev/1/run_validation.sh` — spins up one server with hybrid + LoRA + prefix support enabled, then drives a **3-phase mixed workload** to demonstrate the dashboard captures pool transitions:

- Phase A (0–60 s): random short prompts, no LoRA. KV pool is the binding pool; pool gauges should show KV rising, LoRA flat, mamba flat.
- Phase B (60–120 s): switch to LoRA-skewed traffic across 8 adapters with `max-loras-per-batch=2`. LoRA pool should saturate (`lora_pool_utilization → 1.0`); LoRA evictions visible.
- Phase C (120–180 s): switch to multi-turn long-context traffic. Prefix cache hit rate should rise into the 70–80 % range; `kv_evictable_tokens` grows; eventually if KV under-budgeted, retractions visible.

The dashboard PNG should show three distinct phase regimes with the binding pool changing each phase. That's the whole pitch in one image — a static partition is wrong for at least two of the three phases.

## 5. Results

Validation run executed end-to-end on GPU 1 (idle), Qwen3-4B + 8 synthetic LoRAs (rank 16, generated in Phase 0), `--mem-fraction-static 0.4 --max-loras-per-batch 4 --max-loaded-loras 8`. 60 s per phase, 185 metric samples (one per second). Driver: [`1/run_phase1_validation.sh`](1/run_phase1_validation.sh).

![Phase 1 dashboard](1/validation.dashboard.png)

**Per-phase summary** (extracted from `validation.metrics.jsonl`):

| Phase | Workload | `lora_util` peak | `kv_evictable` (tokens) | `cached_tokens_total` Δ over 60 s |
|---|---|---:|---:|---:|
| **A** (random short, no LoRA) | 480 reqs @ 8 rps | **0 %** | 16K → 22K | 854 |
| **B** (LoRA-skewed) | 480 reqs @ 8 rps | **75 %** | 23K → 48K | 1 269 |
| **C** (multi-turn shared prefix) | 240 reqs @ 4 rps | 0 % (LoRA quiesces) | 48K → 66K | **16 278** |

**Read.**

- **Each phase has a distinct binding-pool signature visible in the dashboard:**
  - Phase A: LoRA pool flat at 0 (no adapter use), KV evictable rises slowly, throughput steady.
  - Phase B: LoRA pool jumps to 0.4–0.75 utilization with visible swap-in/out churn (`lora_used` oscillates 1–3 of 4 slots) — adapter cache is the active scheduler input.
  - Phase C: LoRA pool returns to idle, but `cached_tokens_total` rate spikes 19× — the prefix cache absorbs the multi-turn locality, and `cache_hit_rate` peaks at 0.5 within the phase.
- **Dashboard captures the exact transitions Phase 2 needs to react to.** A budgeter reading these signals every second would see (i) LoRA-bound phase B requires slot growth, (ii) prefix-bound phase C requires KV evictable headroom, (iii) baseline phase A leaves both pools idle. None of the transitions is invisible to `/metrics`.
- **Signal-to-noise sanity.** `kv_evictable` rises monotonically across the 3 phases (16K → 66K) because the KV pool is over-provisioned (mem-fraction=0.4 → max=347K tokens), so blocks accumulate without eviction. This is benign — Phase 2 will care about *the rate of change* of `kv_evictable` (i.e., the eviction rate when the pool is full), not the absolute level.
- **Eviction & retraction signals stay 0** throughout — at this scale the workload doesn't pressure KV enough to trigger preemption. This is expected; Phase 0's Sweep 3 v2 attempt produced retractions when actually pressured. Phase 2 validation will need a workload that pushes the budgeter into the eviction regime.

**Caveat.** The dashboard is currently a *static* PNG generated post-run from a JSONL. For live debugging during Phase 2 development, a `--live` mode is on the to-do list (re-render every second from a tail of the JSONL).

## 6. Phase 1 done — handoff to Phase 2

Phase 1 ships:
- A documented signal contract (§1) — 24 named signals, all already exported by SGLang.
- [`1/sample_metrics.py`](1/sample_metrics.py) — drop-in `/metrics` sidecar (60 LoC).

Total: **~390 LoC of instrumentation**, no SGLang patches. Signal model is end-to-end validated.

Phase 2 ([`2.md`](2.md)) will use these signals to drive an online budgeter on top of `UnifiedRadixCache`. The first thing Phase 2 should do is replay Phase 1's 3-phase validation against its budgeter and confirm the policy reacts correctly to each transition.

## What Phase 2 inherits

- A documented signal contract (§1) — 24 named gauges/counters, all already exported by SGLang.
- `dev/1/sample_metrics.py` — drop-in sidecar that produces the JSONL Phase 2 will subscribe to.

The signal model is validated end-to-end before Phase 2 ever touches the allocator. If a signal turns out to be unobservable or noisy, we know in Phase 1 — not after we've built the policy on top.
