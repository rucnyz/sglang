# Phase 2 — Cross-pool physical reallocation via VMM (= paper's Layer 2)

**Status:** scaffolding shipped (alpha); cross-pool actuator design in progress (2026-04-29).

**Goal.** A budgeter that physically reallocates HBM bytes across the four pools (paged KV / live SSM / LoRA / prefix-cache) at phase timescale based on observed $V_\sigma(m_\sigma)$ pressure. Composes with the within-pool design (= paper's Layer 1, Phase 3 on SGLang).

**Why physical, not logical.** The first iteration shipped here used `UnifiedRadixCache.evict(EvictParams)` as the only actuator — that lets the budgeter shift bytes WITHIN paged-KV (active vs evictable prefix) but cannot move bytes ACROSS pools. Random-uniform A/B (`dev/2/norep/`) showed within-pool actuation is bit-equivalent to baseline at ±0.4% — confirming no-regression but also that the within-pool lever alone doesn't capture the paper's claim. The cross-pool problem requires runtime VMM-aware tensor resize, which the next sub-phase 2e tackles.

**Prerequisite.** Phase 1 done; Layer 1 within-pool design ready (Phase 3) or stubbable for the cross-pool demo.

---

## 1. Architecture

The budgeter lives **in-process** with the SGLang scheduler. Out-of-process control is too slow (≥100 ms RPC + queueing) for sub-second reactions, and the actuation API we need is not exposed externally.

```
┌──────────────────────────────────────────┐
│      SGLang scheduler (Python)           │
│  ┌─────────────────────────────────────┐ │
│  │   step() loop                       │ │
│  │      ├── recv requests              │ │
│  │      ├── alloc / decode / commit    │ │
│  │      └── BudgetController.tick() ◀──┼─┤   every K iterations (~1 s)
│  └─────────────────────────────────────┘ │
│  ┌─────────────────────────────────────┐ │
│  │   BudgetController                  │ │
│  │      ├── snapshot from SchedulerStats│ │
│  │      ├── fit V_σ from history       │ │
│  │      ├── Lagrange equalize          │ │
│  │      └── actuate                    │ │
│  └────────────────┬────────────────────┘ │
│                   │                       │
│      ┌────────────┼─────────────┐         │
│      ▼            ▼             ▼         │
│  UnifiedRadix LoRAManager  ScheduleArgs   │
│  Cache.evict ↑.set_capacity ↑.max_running │
│              ↑                            │
└──────────────┴────────────────────────────┘
```

The actuation surface is three calls:

1. **`tree_cache.evict(EvictParams)`** — already exists. Releases tokens from full-attn KV / SWA / Mamba prefix caches per pool target. Exposed by `UnifiedRadixCache` (gated by `SGLANG_ENABLE_UNIFIED_RADIX_TREE=1`).
2. **`lora_manager.set_capacity(n)`** — *to be added*. Mutate `max_loras_per_batch` at runtime. ~30 LoC patch.
3. **`scheduler.set_max_running(n)`** — *to be added*. Mutate `max_running_requests` at runtime. ~10 LoC patch.

## 2. Policy

### 2.1 Marginal utility estimation

For each pool σ, fit $V_\sigma(m_\sigma)$ from the last 60 s of observations:

- $m_\sigma$ — current allocation (tokens or slots)
- $u_\sigma$ — utility proxy (per pool, see below)

Utility proxies:

| Pool | Utility proxy $u_\sigma$ |
|---|---|
| Paged KV (full attn) | `gen_throughput * (1 - num_paused/num_running)` — if paused requests grow, utility drops |
| Paged KV (prefix portion) | `cache_hit_rate * cumulative_cached_tokens_rate` — value of holding evictable blocks |
| SSM / DeltaNet | `gen_throughput / (mamba_usage)` if pegged at ≈1.0; else 0 (slack) |
| LoRA | `1 - (lora_pool_utilization == 1.0 ? lora_eviction_rate : 0)` — utility drops when LRU thrashes |

The slope $\partial V_\sigma / \partial m_\sigma$ is estimated by finite differences over the recent window. We do *not* need accurate $V_\sigma$ — only its slope sign and rough magnitude.

### 2.2 Lagrange equalization

Subject to $\sum_\sigma m_\sigma = M$ (fixed), the optimum satisfies $\partial V_\sigma / \partial m_\sigma = \lambda$ for all $\sigma$. The budgeter computes target $m_\sigma^\star$ by:

1. Rank pools by current slope (descending).
2. Move a small step $\Delta$ (capped at e.g. 5% of pool size per tick) from the lowest-slope pool toward the highest-slope pool.
3. Repeat until slopes are within tolerance ε or step budget exhausted.

### 2.3 Rate-limit & hysteresis

- Tick interval: 1 s. Each tick does at most one ε-step.
- Hysteresis: don't reverse a transfer for 5 s after an action.
- Floor / ceiling: each pool gets at minimum 5% of $M$ and at most 70% of $M$.

This keeps the policy stable under noisy signals.

## 3. Implementation plan

Sub-phases, each independently testable:

### 2a. In-process scaffolding (read-only)

- New file `python/sglang/srt/budgeter/agent.py` (~120 LoC): `BudgetAgent` class. Has `tick()` method that snapshots pool state and writes a JSONL line; no actuation.
- Patch `python/sglang/srt/managers/scheduler.py`: instantiate agent in `__init__` if env `SGLANG_BUDGETER=1`, call `agent.tick()` every K iterations.
- Patch `python/sglang/srt/observability/scheduler_metrics_mixin.py`: pass through the LoRA / mamba / radix references the agent needs.

**Deliverable:** server boots with budgeter on, JSONL appears, no behaviour change.

### 2b. Actuation: UnifiedRadixCache.evict

- Add policy module `python/sglang/srt/budgeter/policy.py` (~100 LoC): `LagrangePolicy.compute_evict_targets(snapshot) -> EvictParams`.
- In `agent.tick()`, when `SGLANG_BUDGETER_ACTUATE=1`, call `tree_cache.evict(targets)`.
- Add metrics: `sglang:budgeter_evict_kv_tokens_total`, `sglang:budgeter_evict_mamba_total`, `sglang:budgeter_decisions_total`.

**Deliverable:** budgeter actively evicts; server still serves correctly under all Phase 1 workloads.

### 2c. Actuation: LoRA capacity

- Patch `python/sglang/srt/lora/lora_manager.py`: add `set_capacity(int)` that mutates `self.max_loras_per_batch` and `self.max_loaded_loras` at runtime, growing/shrinking the underlying tensor pool. ~50 LoC.
- Add to `LagrangePolicy`: when LoRA is the binding pool, increase `max_loras_per_batch` (within ceiling).

**Deliverable:** LoRA cache resizable at runtime; budgeter expands it during phase-B-like traffic.

### 2d. Validation

- Re-run Phase 1's 3-phase mixed workload twice: budgeter OFF (baseline) and budgeter ON.
- Compare per-phase throughput, TTFT, pool utilization. Target: budgeter wins ≥10 % aggregate throughput with no SLO violation increase.
- Render comparison plot.

## 4. Scope discipline

Out of Phase 2 (deferred to Phase 3 or future):

- **Physical pool resize.** EvictParams shifts logical ownership inside the unified-radix tree but does not grow/shrink the int8 byte buffer that backs the pool. That requires `torch_memory_saver` VMM remap, deferred to Phase 3.
- **Multi-rank coordination.** TP > 1 needs each rank to agree on the budget. Phase 2 targets TP=1 only.
- **Workload prediction.** The policy reacts to observed pressure, not predicted. ML-driven prediction is future work.

### 5.1 Honest status (after 2026-04-29 audits)

Earlier I considered whether Layer 1's snapshot machinery (host-tiered big pages) might subsume the cross-pool VMM problem under a big-page LRU. Subagent code-level audit refuted that: snapshot mechanisms of this shape live on the host (pinned CPU) tier, not GPU; GPU pool tensors are still independent `torch.empty` allocations bound at startup. Net: Layer 1 sharpens $V_{\text{prefix}}$ on hybrid models (= more reason for the budgeter to care about prefix budget) but does NOT physically expose cross-pool reallocation. Layer 2 has to be built explicitly (= 2e), extending SGLang's existing per-region VMM allocator to per-chunk granularity.

### 5.3 No-regression policy (post-noise-fix) — verified 2026-04-29

After the first smoke A/B showed budgeter ON ~5 % slower on random-uniform traffic, the policy was tightened to only trigger on SGLang's failure-mode signals:

- `num_queue_reqs ≥ 1`, OR
- `num_paused_reqs > 0`, OR
- `num_retracted_reqs > 0`.

`token_usage`-based proactive triggers were removed — high pool usage with a calm queue means the system is performing fine; evicting would only thin a cache about to be useful. With this gate, on workloads where SGLang already keeps up the budgeter never actuates → 0 cost → bit-identical behavior to baseline. **No-regression is enforced by the policy, not by tuning.**

**Verified A/B (3 trials each arm, Qwen3-4B, mem-fraction-static=0.15, 1000 prompts × 1024-in/256-out @ 64 rps, `SGLANG_ENABLE_UNIFIED_RADIX_TREE=1`):**

|---|---:|---:|---:|---:|---:|---:|---:|
| off | 70.7 | 844.6 | 1540.8 | 3428.5 | 27 618 | 6 942 | — |
| on  | 68.4 | 818.5 | 1527.5 | 3431.4 | 27 483 | 6 908 | **0** |
| Δ   | −3.2 % | −3.1 % | −0.9 % | +0.1 % | −0.5 % | −0.5 % | — |

All deltas within trial-to-trial noise (one of three trials had ON slightly slower, two had it slightly faster; no systematic bias). **0 actuations across 3 trials, ~22 K total ticks** — confirms the policy is silent on healthy workloads.

### 5.4 Workload commands for the real demo (Phase 2d)

A workload where prefix cache holds memory that becomes dead weight after a phase shift:

- **Phase A (60 s)**: multi-turn shared-prefix traffic populates prefix cache to ~40 % of pool.
- **Phase B (60 s)**: traffic switches to random un-shared prompts; cached prefixes from A are now stale. With budgeter OFF those blocks stay until natural eviction; with budgeter ON the policy detects retraction/pause and pre-evicts. We expect phase-B TTFT/throughput to recover faster with budgeter ON.

Concrete commands. Run on an idle GPU (e.g. GPU 1). Pick a tight `mem-fraction-static` so the pool actually saturates during phase B — `0.15` worked in smoke; tune as needed.

**A. Common server launch (use this template; vary the budgeter env vars per arm):**

```bash
cd /scratch/yuzhou/projects/sglang
set -a; source .env; set +a
PATH="$PWD/.venv/bin:$PATH" CUDA_VISIBLE_DEVICES=1 \
  SGLANG_ENABLE_UNIFIED_RADIX_TREE=1 \
  $BUDGETER_ENV \
  python -m sglang.launch_server \
    --model-path Qwen/Qwen3-4B \
    --port 30003 --host 127.0.0.1 \
```

For the **baseline arm**: `BUDGETER_ENV=""`.
