# T34 — multi-axis sparse 0/1 knapsack DP (#156, DESIGN §9)

The exact-DP core of the **value-gated** policy.  DESIGN §9 takes only
net-positive actions and may no-op, so every phase runs ONE
value-maximising primitive:

* **`knapsack_max_value_multi`**: max-total-net-value subset whose
  per-(tier, subpool) `re_use` stays within `budget` (≤ axes); the empty
  set is always a candidate.  `joint_decide` feeds it BOTH the relief
  value-items (a Migrate wrapped as gain = −cost, `re_use` = destination
  `acquired`, budget = DRAM/DISK free room) and the Resume candidates
  (gain = V_u, `re_use` = HBM re-entry, budget = per-HBM-subpool free
  room).

The earlier min-cost-**cover** primitive (`knapsack_min_cost_multi`, with
its `best_effort` forced-relief fallback) was REMOVED in the value-gated
rewrite — it forced relief against an unrelievable subpool and caused the
A3 agent-stall regression.  There is no cover target and no infeasibility:
"nothing relieves the pressure" is just the empty plan.

Multi-axis because items consume bytes from *different* (tier, subpool)
budgets; each axis quantises at its own `page_bytes` (per-axis
`bucket_size`, no global collapse).  Sparse: only reachable `dp` cells
materialise (a dense table is exponential in axis count).

Lives in `baselines/knapsack.py` with the candidate contract
(`Migrate(cost, relief, acquired)`, `Resume(gain, re_use)`; sparse
`{tier: {subpool: bytes}}`, string tier keys matching the §5/§6 wire).
`Pause(cost, relief)` is retained as a DORMANT lever (not generated by
`joint_decide`).

## DESIGN-vs-CODE CORRECTION

**Parent-pointer reconstruction** (not the DESIGN pseudocode's
subtract-the-delta traceback).  Once the DP runs over **multiple-choice
groups** (`group=unit hash`), a subtract-by-item-index readout cannot
tell which member of a group was taken; recording the predecessor state
per improving transition (`parent[(gi, s_new)] = (s, member)`) makes the
chosen-subset readout exact.  Verified against the exhaustive oracle.

## STAGES (8)

```
D. value-max core
  D0 single budget axis: max-gain subset within budget
  D1 EXACT vs brute force — 60 random fixtures (bucket_size=1, +/- gains:
     a net-negative pick must lose to the empty set)
  D2 budget HARD; re_use rounds UP (1B → 1 bucket → only one fits a
     1-bucket budget)
  D3 returned subset feasible + optimal
G. grouping (#194)
  G0 multiple-choice: candidates sharing a non-None group are at-most-one
     (a unit's evict/spill/DROP are alternatives — taking two would
     double-count its bytes).  EXACT vs a grouped brute oracle (60 random,
     2 axes), incl. the same-budget case a plain 0/1 would mis-stack.
E. audit closure
  E0 EXACT vs a quantising brute oracle at bucket_size>1, MULTI-AXIS
  E1 DP cell ceiling fails loud (KnapsackBudgetExceededError + forensic
     ctx) past max_dp_cells, instead of stalling the event loop (#9)
  E2 empty items / zero budget / all-negative gains → empty plan (the
     value-gated no-op) (#12)
```

The brute-force oracle (exhaustive subset / per-group enumeration) is the
gold standard for an exact DP; at `bucket_size=1` the DP works in raw
bytes so DP-optimum == brute-optimum exactly (180 random fixtures total).
